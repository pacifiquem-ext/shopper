# AGENTS.md — Working Constitution for OnlineShop.rw

This file governs every agent (Claude Code, Grok, or otherwise) working in this repository. It is not
optional background reading — it is the contract. If something you're about to do conflicts with
this file, stop and resolve the conflict (ask the user, or propose an edit to this file) before
proceeding.

This document is itself living. When the user gives standing instructions during a session
("always do X", "never do Y"), fold them back into this file in the same session rather than
letting them live only in chat history.

---

## 1. Where we are, where we're going

**OnlineShop.rw** is a multi-tenant marketplace and store-operating platform for Rwanda: merchants
launch online retail stores, manage products/inventory/orders/delivery
zones, accept payments, and grow via Basic → Pro plan upgrades. Buyers browse the marketplace,
shop storefronts, checkout, and track order status. Full product intent lives in [`README.md`](./README.md)
(vision, pricing, journeys, modules, and explicit out-of-scope list).

The repository is a **pnpm monorepo** (`client/` + `server/` + `packages/shared`) in active build-out:

- **Client:** Next.js (App Router) + React + TypeScript + Tailwind + AlignUI + next-intl + Zustand + Axios (`@onlineshop/client`)
- **Server:** NestJS + TypeScript + Prisma + PostgreSQL + Redis/Bull + JWT auth + nestjs-i18n + Pino (`@onlineshop/server`)
- **Shared:** `@onlineshop/shared` — API envelope types, domain status constants, store template IDs
- **Dev:** from repo root run `pnpm dev` (shared build/watch + Nest + Next in parallel)

The mission: ship a **fully functional, production-grade, fast full-stack application** — not a
presentational shell — **built by AI agents** held to professional engineering standards. Every
backend change — schema, route, service, job — is implemented by an agent, and the same agent (or
the one that picks the work back up) is responsible for wiring it all the way through to the
frontend. A backend endpoint with no caller, or a frontend still reading mock/local-only data next
to a real endpoint it should call instead, is unfinished work, not two separate tasks.

**Functional does not mean it's allowed to look or feel worse.** The existing UI (shadcn/ui base,
dashboard chrome, storefront templates, loading/error/empty patterns in the design system) was
built to a consistent, premium standard, and that standard is a **requirement**. Every real
loading/error/empty/success state introduced while wiring up the backend must match that polish —
a working feature with a raw browser spinner, an unstyled error string, or an inconsistent empty
state is not "done." If a new state doesn't have an obvious design-system answer, treat that as a
"stop and ask" case (§15), not a license to improvise something inconsistent.

**Coding standards are mandatory, not optional.** Before writing or changing code:

| Layer | Required reading |
| ----- | ---------------- |
| Frontend (`client/`) | [`.agents/rules/client-coding-standards.md`](./.agents/rules/client-coding-standards.md) |
| Backend (`server/`) | [`.agents/rules/server-coding-standards.md`](./.agents/rules/server-coding-standards.md) |
| Any user-visible text | [`.agents/rules/i18n-standards.md`](./.agents/rules/i18n-standards.md) |

Do not assume architecture, styling, layer contracts, or i18n conventions without those documents.

**A note on inherited / generated code:** treat any code generated by an external tool, template, or
boilerplate — not written by an agent in this project — with the same suspicion you'd apply to an
unreviewed third-party dependency. Skim generated config files for anything that doesn't look like
what it claims to be before running scripts against them (lint, build, install hooks).

## 2. Prime directives (non-negotiable)

These override convenience, speed of typing, or "I think this is probably fine."

1. **Stop and ask when unsure.** If a requirement is ambiguous, a decision is hard to reverse
   (schema design, auth strategy, a new paid vendor/API, deleting data, changing a public
   contract), or you're choosing between two reasonable approaches with no clear winner — **stop
   and ask the user**. Do not guess and move on. Speed matters, but a wrong foundational decision
   is slower to fix than a 30-second question.
2. **No dummy data, no fake delays, no simulated state, no stubs — anywhere.** Every `useState`
   seeded with hardcoded arrays, every `setTimeout(() => fakeSuccess(), 1500)`, every "pretend this
   succeeded" flow, every empty controller/page that only says "coming soon," must become a real
   API call with real loading/error/success states — **styled to the same design-system standard as
   the rest of the app**, not a functional-but-unpolished afterthought. See §10 for the inventory of
   what to hunt. If a feature cannot be finished end-to-end in this session, leave it on `TODO.md`
   as Pending — do not land a non-working shell that pretends to be done.
3. **Backend work isn't done until it's integrated — visually as well as functionally.** All
   backend implementation in this project is done by AI agents, end to end — that includes making
   the frontend actually call the new endpoint (via the service layer) and render real
   data/error/loading states with the same consistency and premium feel as existing screens.
   Shipping a route with no consumer, leaving the UI on mock data "for now," or wiring real data
   behind an inconsistent or unstyled UI state is unfinished work.
4. **Production-grade, not prototype-grade.** Every piece of backend code should be written as if
   it ships to real users today: input validation (DTOs), error handling, auth/tenant checks, rate
   limits, structured logging, no secrets in code. See §12.
5. **Reuse relentlessly. No repetition.** Before writing a function, type, API client, hook, DTO,
   or validation schema, search for an existing one. Three similar lines is fine; a third copy of
   the same 20-line block is not — extract it. Apply the `codebase-design` skill's "deep module"
   thinking: small interfaces, real implementation behind them, one place to fix bugs. This is a
   standing preference of the project owner — treat it as strict, not aspirational.
6. **Minimal comments.** Default to zero comments. Code should read clearly from naming and
   structure. Only write a comment when it captures a non-obvious _why_ (a workaround, a hidden
   constraint, a subtlety that would surprise a reader) — never a comment that restates _what_
   the code does.
7. **Test what you build.** Use the `tdd` skill for new logic where it applies. At minimum: every
   API endpoint has a test proving its contract; every non-trivial function has a test proving its
   behavior at its public seam. Run typecheck + lint + tests before considering a task done.
8. **Keep `TODO.md` and `ENV.md` current.** See §14 and §7. Update them as part of the task, not
   after — if you finish a slice of work without updating these, the task isn't done. These files
   are full living ledgers (not stubs): every env var and every actionable backlog item that
   matters must be accurate and complete enough that the next agent can work without archaeology.
9. **End every implementation session with a `TODO.md` status report** — see §14.1. Open with at
   most **three short lines** on overall project state **including rough completion percentages**,
   then tables. **Done** lists only what this session completed and we know works. If anything in
   the session's target scope remains open, **Pending** (and **Skipped** where applicable) use the
   full structural layout in §14.1. Categories are mutually exclusive; no duplicate rows.
10. **Use MCP servers where one exists for the job**, instead of shelling out to raw CLI calls or
    hand-rolled scripts against the same system (database, GitHub, filesystem, browser, etc.). MCP
    tools are typically better-scoped, safer, and give the user better visibility into what you did.
    If no MCP exists for something you do repeatedly, say so — the user may want to add one.
11. **Never fabricate success.** Don't report a task complete because tests weren't written to
    catch the failure, or because you didn't run something. If you didn't verify it, say so.
12. **Never commit, push, or merge without explicit user approval after review.** Do **not** run
    `git commit`, `git commit --amend`, `git push`, `gh pr create`, `gh pr merge`, force-push, or
    any other git history / remote-publishing action unless the user has clearly approved **that
    specific action in the current turn** after they have had a chance to review the diff (e.g.
    "commit this", "looks good, commit", "push this branch", "open the PR", "merge it").
    Implementing and editing files in the working tree is fine. When a slice is ready, summarize
    what changed, point to the diff (`git status` / `git diff`), and **ask** before creating a
    commit; then ask again before push/PR/merge. A prior approval in an older session does **not**
    carry forward. "Ship it" / "commit and push" in the same message counts as approval only for
    the actions named. This standing rule overrides convenience or prior session habits.
13. **i18n is mandatory for all user-visible text.** English (`en`) and Kinyarwanda (`rw`) must
    stay in absolute key parity on client and server. Hardcoded user-facing strings are a defect.
    See §9 and [`.agents/rules/i18n-standards.md`](./.agents/rules/i18n-standards.md). A change that
    adds UI/API copy without both locales is incomplete.
14. **Cross-stack contracts stay compatible.** When you change a DTO, response shape, auth rule, or
    status enum, update server **and** client (types, services, validations, UI) in the same task.
    Never leave the two packages disagreeing about a public contract.

## 4. Technology baseline

These are the project's current decided defaults. Treat them as the default path; if you hit a real
reason one is wrong for a specific requirement, **stop and confirm the change with the user rather
than silently deviating**, and update this section when they do.

- **Language:** TypeScript everywhere (client and server). No `any` unless justified inline with a
  one-line why.
- **Frontend framework:** **Next.js** App Router (React Server Components by default; `'use client'`
  only when required). Fast refresh / SWC via Next's toolchain. `tsc --noEmit` for typecheck.
- **UI:** Tailwind CSS v4 + **AlignUI v1.2** tokens (`globals.css`) and free base components under
  `client/src/components/alignui/`. Legacy shadcn-compatible bridges in `client/src/components/ui/`
  are restyled to AlignUI tokens. Icons: **Remix Icon**. Toasts via **sonner** — not `window.alert` / `confirm` / `prompt`. See `design-system/MASTER.md`.
- **Client state:** **Zustand** for cross-component state; local `useState` for purely local UI.
- **Client data access:** **Axios** instance in `client/src/lib/axios.ts` + domain services in
  `client/src/services/`. Do not scatter raw `fetch` / ad hoc Axios instances.
- **Client validation:** **Zod** in `client/src/validations/`; env via `@t3-oss/env-nextjs` in
  `client/src/env.ts`.
- **i18n (client):** **next-intl** — locales `en` and `rw` under `client/src/i18n/locales/`.
- **Backend runtime/framework:** **NestJS** on Node.js (≥20), Express adapter, URI versioning
  (`/v1/...`).
- **Compiler (server):** Nest CLI build; **SWC** available for Jest/tooling. `tsc` for type-checking
  as configured by the package.
- **Database:** **PostgreSQL** with **Prisma** as ORM/migration tool. Schema:
  `server/prisma/schema.prisma`. Prefer Neon (or any Postgres) via `DATABASE_URL` in real deploys;
  local via Docker Compose (`server/docker-compose.yml`).
- **Cache / queues:** **Redis** (`REDIS_URL`) + **Bull** (`@nestjs/bull`) for background work that
  must not block the request cycle. Local Redis via Compose.
- **Auth:** JWT access + refresh (`AUTH_ACCESS_TOKEN_*`, `AUTH_REFRESH_TOKEN_*`), Passport strategies,
  argon2/bcrypt password hashing as already used in auth module. Tenant/store scoping via common
  tenant helpers — never trust client-supplied store ownership without server checks.
- **Validation (server):** **class-validator** + **class-transformer** DTOs on every controller
  input; global `ValidationPipe` (whitelist + forbid non-whitelisted). Do not accept raw `body: any`.
- **API docs:** Swagger/OpenAPI for non-production (`server/src/swagger.ts`).
- **Logging:** structured logging via **Pino** (`nestjs-pino`). No `console.log` in server
  production paths.
- **Observability:** optional **Sentry** (`SENTRY_DSN`) via app config.
- **HTTP hardening:** Helmet, compression, throttling (`@nestjs/throttler`), CORS from config.
- **i18n (server):** **nestjs-i18n** — message files under `server/src/languages/{en,rw}/`.
- **Package managers:** **pnpm workspace** at repo root (`pnpm-workspace.yaml`). Shared must build first (`pnpm build:shared`).
- **Testing:** **Vitest** + Playwright e2e on the client; **Jest** + Supertest patterns on the
  server (`nestjs-best-practices` test rules).
- **Formatting & linting:** Prettier + ESLint on both packages (`eslint-config-prettier` so they
  don't fight). Run both — Prettier is not a substitute for lint rules.

If a task requires a technology not listed here (a new SaaS dependency, a new datastore, a paid
payment provider, a new AI vendor), that's a hard-to-reverse decision — **stop and ask**, then add
it to this section once decided.

### Explicitly out of product scope (do not build unless the user reopens)

From product strategy (`README.md` §9): rider marketplace, live tracking maps, AI forecasting,
multi-currency, social integrations, mobile apps, advanced marketing automation. If a task drifts
into these, surface it and confirm before investing work.

## 5. Performance & optimization (production is fast by default)

Speed is a first-class requirement, not a follow-up pass. Apply the technique that fits the layer
you're touching:

**Database**

- Index every column used in a `WHERE`, `ORDER BY`, or join — add the index in the same migration
  as the query that needs it.
- Select only the fields a response actually needs; don't fetch full rows/relations "just in case."
- Always paginate list endpoints — never return an unbounded array from a list API.
- Avoid N+1 queries: batch/`include` related data deliberately, don't loop-and-query.
- Reuse the Prisma client singleton from the common database module; don't instantiate
  `PrismaClient` per request.

**API & backend**

- Push anything slower than a user is willing to wait for (exports, bulk imports, heavy reports,
  external payment provider round-trips that can be async) into a background job — request handlers
  return fast and let the client poll/subscribe for completion when needed.
- Validate and reject bad input as early as possible (DTO pipe), before any DB/external work.
- Use HTTP compression and appropriate cache headers on responses that can be cached.
- Respect throttling defaults; don't disable rate limits without a documented reason.

**Frontend**

- Prefer Server Components; keep client bundles lean (`'use client'` only when required).
- Route-level and component-level code splitting where Next already supports it; don't ship dead
  weight in the merchant dashboard to the public storefront and vice versa.
- Cache and dedupe server requests where the UI re-fetches the same resource; avoid hand-rolled
  `useEffect` fetch-and-store duplication when a service + store pattern already exists.
- Virtualize or paginate long tables (orders, inventory, products) instead of rendering every row.
- Optimize and lazy-load images/static assets (`next/image` where appropriate).

**Build & tooling**

- Rely on Next/Nest production builds; don't disable tree-shaking or minification without cause.
- Keep `pnpm` installs clean; don't add dependencies "just in case."

None of this licenses premature optimization — don't add caching layers or background jobs for
paths that aren't actually slow. Apply these where the workload genuinely calls for them (large
lists, external I/O, payments, bulk operations), not everywhere reflexively.

## 7. `ENV.md` contract

`ENV.md` (root) is the single source of truth for every environment variable in the project — what
exists, what it's for, and whether it's actually been set up (vs. just documented as a placeholder).
Real `.env` files are gitignored and never committed; `ENV.md` plus each package's `.env.example`
(when present) are how anyone knows what's needed.

**Read `ENV.md` at the start of every session** before touching config. **Update it at the end of
every session** in which you added, removed, renamed, or changed the meaning of an env var —
introducing a new var means updating `ENV.md`, the relevant `.env.example`, and the validation
site (`client/src/env.ts` and/or `server/src/common/config/*` / `ConfigService` reads) together,
not `ENV.md` "later."

`ENV.md` is the full inventory (server, client, Docker Compose, seed, planned-but-unimplemented).
Do not let new vars exist only in code or only in chat. Package templates:

- `server/.env.example` → copy to `server/.env`
- `client/.env.example` → copy to `client/.env.local`

Local quickstart and status meanings (`required` / `optional` / `local-only` / `planned`) live in
`ENV.md` itself — keep those tables complete when the surface area changes.

## 9. Domain model & i18n quick reference

### Domain

Canonical product language lives in [`README.md`](./README.md) and, when maintained,
[`CONTEXT.md`](./CONTEXT.md). Prisma models and enums are the source of truth for persisted shape
(`server/prisma/schema.prisma`): users/roles, stores/status, products/inventory, orders/fulfillment,
payments, delivery zones, OTPs, etc.

Core domain modules today (server): `auth`, `onboarding`, `products`, `inventory`, `orders`,
`delivery-zones`, `catalog`, `store-settings`, `analytics`, `admin`, `references`.

When you invent a new term or entity, update `CONTEXT.md` (create it with the `domain-modeling`
skill if missing) rather than letting jargon live only in chat.

### i18n (mandatory)

Full rules: [`.agents/rules/i18n-standards.md`](./.agents/rules/i18n-standards.md).

- **Client:** `client/src/i18n/locales/en.json` and `rw.json` — same keys always. Use
  `useTranslations` / server-side next-intl helpers; never hardcode user-facing strings.
- **Server:** `server/src/languages/en/*` and `server/src/languages/rw/*` — same structure. Use
  `I18nService` / nestjs-i18n; never hardcode exception or validation messages for end users.
- **Parity is absolute:** adding a key to `en` without `rw` (or vice versa) is incomplete work.
- Prefer descriptive domain keys (`auth.errors.invalidPassword`, not `error1`).

## 10. Dummy data / dev-fallback inventory (must be replaced, not decorated)

Nothing here is exhaustive — before declaring a path "done", grep for patterns like:

- `useState<.*\[\]>` seeded with literals
- `MOCK_`, `mock`, `EXAMPLE_`, `INITIAL_`, `dummy`, `fakeSuccess`
- silent catch blocks that swallow API failures and show empty success
- client cart/catalog still reading only localStorage when a server source of truth exists

**Client patterns that are legitimate (not mocks)**

- Debounce timers (subdomain availability checks), short UI pulse timeouts (cart/wishlist feedback),
  toast auto-dismiss — these are UX timing, not simulated business success.
- Local cart storage helpers used for guest shop UX — still must reconcile with real checkout/order
  APIs when the buyer completes a purchase.

**Replaced / real integrations (do not reintroduce mocks)**

- Auth flows, store onboarding, merchant dashboard domains that already call `services/*` against
  the Nest API — keep them on real endpoints with real error toasts and loading states.

**Still watch carefully**

- Any dashboard widget that charts or totals without calling analytics/orders APIs.
- Payments and subscription/plan enforcement — must be real provider + real plan gates when
  productized; do not fake "payment succeeded" in the UI.
- Storefront catalog when marketplace/store data should come from `catalog` / public APIs.

Each remaining mock becomes a real integration with genuine loading/error/empty states — not a
reskin of the same fake timeout (§1, §2.2).

## 11. Coding standards (summary)

Full detail lives in the rule files; this section is the non-negotiable summary.

### Cross-cutting

- **Reuse over repetition** (§2.5). Don't hand-duplicate a DTO shape on both sides without need;
  when you must mirror, keep names and fields aligned and update both in one task.
- **Deep modules, small interfaces** — per `codebase-design`. Controllers thin; services own
  orchestration; repositories own queries.
- **Errors are typed and handled centrally** — domain exceptions + response filters/interceptors on
  the server; Axios interceptors + sonner toasts on the client. No bare `throw "string"`, no
  swallowed catches that hide failures from the user.
- **No secrets in code** — all keys/credentials via environment variables, never committed.
  `.env.example` and `ENV.md` (§7) document every variable.
- **Naming** — PascalCase components/classes; camelCase functions/variables/hooks; kebab-case
  feature filenames on the client; Nest module folder conventions on the server. Match neighbors.
- **No speculative abstraction** — build the interface the current requirement needs; don't add
  config/flags/extension points for a hypothetical future case.
- **AlignUI components** — prefer `client/src/components/alignui/*` for new work; keep `ui/*` bridges
  token-aligned. See `design-system/MASTER.md`.

### Client layer contracts (see client-coding-standards)

- Default **Server Components**; `'use client'` only when required.
- All routes under `app/[locale]/`; use `@/i18n/navigation` + `ROUTES`.
- Pages/components call **services**, not raw Axios, for domain APIs.
- Zustand for shared client state; no prop-drilling of auth/session.

### Server layer contracts (see server-coding-standards)

- Domain modules under `server/src/modules/{domain}/`.
- Controllers: HTTP only. Services: business logic only. Repositories: DB only.
- Dependencies flow **downward** only; no circular module imports.
- DTOs validate every external input.

## 12. Production-readiness checklist

Apply this before calling anything "done":

  clients in production.
- Rate limiting on public-facing and auth-sensitive routes (respect existing throttler config).
- Structured logs on request lifecycle and errors (Pino) — no `console.log` as the primary log path.
- Long-running work is backgrounded when it would block a request unacceptably.
- Health/readiness endpoints exist or are extended (Terminus patterns) — don't invent a second
  parallel health system.
- Prisma connection lifecycle is shared and closed on graceful shutdown in production.
- No silent `TODO`/`FIXME` left in shipped code — it goes in `TODO.md` instead (§14) or gets done.
- Tests cover the contract (typecheck + lint + unit/integration tests green) and you have
  personally exercised the real flow where practical, not just asserted it in a test.
- en/rw i18n parity for any new user-facing strings (client and/or server).
- Client UI states (loading / empty / error / success) match design-system quality.
- Performance techniques in §5 applied where the workload calls for them.
- Cross-stack contract updated on both client and server when the API shape changed.

## 14. `TODO.md` contract

`TODO.md` is the single source of truth for "what's done, what's in flight, what's not started."
Every agent reads it before starting work and updates it as part of finishing a task — not as an
afterthought. It is a full project ledger (foundation through product gaps), not a per-session stub.
Preserve historical **Done** accuracy; add new work to **Next up** / **In progress** as discovered.

Format:

```markdown
# TODO

## In progress

- [ ] Short task description — @who/agent, started <date>

## Next up

- [ ] Task, roughly ordered by priority

## Done

- [x] Task — finished <date>, notes if non-obvious
```

Rules:

- Keep entries short and specific (task, not essay). Link to an ADR or issue if more context is
  needed rather than writing it inline.
- Move an item to **Done** in `TODO.md` only once it passes §12's checklist — i.e. we **know it
  works** (tests + integration + polished real UI states where applicable), not merely that code
  was typed.
- If you discover new work while doing a task (a gap, a follow-up, a piece of debt you
  deliberately deferred), add it to **Next up** immediately — don't let it evaporate.
- Honor prior **Skipped** decisions in the same initiative unless the user explicitly reopens
  them. Carry those skips forward and restate them only in the Skipped table of the §14.1 report
  (never also under Pending).

### 14.1 End-of-session TODO status report (mandatory)

After any session that implements, fixes, or deliberately defers work tracked in `TODO.md`, update
`TODO.md` first, then end the **final user-facing message** in this order:

1. **State blurb (max 3 lines).** Overall project readiness in plain text with **rough
   percentages** (e.g. foundation/schema/auth ~X%, merchant path onboarding→products→orders ~Y%,
   marketplace/checkout/payments ~Z%, Pro growth features / release hardening ~W%). No fourth line
   of status prose before the tables.
2. **Done table** — **only what this session completed** and we know works (§12). Do not reprint
   historical Done from prior sessions.
3. **Pending / Skipped tables** — include these with the full structural layout below **whenever
   anything in the session's target scope is still open** (or when listing the actionable backlog
   the next agent needs). If the session scope is fully verified with nothing left open in that
   scope, Pending may be a single `— | None` row and Skipped `— | None | — | —`.

#### Category definitions (non-overlapping)

| Category | Meaning in the report | Maps from `TODO.md` |
| -------- | --------------------- | ------------------- |
| **Done** | Work we **know works** — verified this session against §12 (not "code exists"). | `[x]` items **completed in this session only** |
| **Pending** | Work that has **never been started** and is **actionable now**. | `[ ]` items **excluding** every Skipped row |
| **Skipped** | A **subset of never-started work** intentionally not begun (blocked or deferred). | `[ ]` items blocked or deliberately deferred |

**No duplication:** each item appears in **exactly one** table.
`Skipped ⊂ never-started backlog`; **Pending** = `never-started backlog ∖ Skipped`.

**Blocked note:** every Skipped row needs a **Blocked** cell (`Nothing — deliberate deferral`,
credential, prior § section, or user decision). Pending rows are not externally blocked.

#### Table templates

**Done** (this session only):

| Section | Item | Notes |
| ------- | ---- | ----- |
| §N … | Short item text | How we know it works |

**Pending** (never started, actionable; omit any Skipped row):

| Section | Item |
| ------- | ---- |
| §N … | Short item text |

**Skipped** (never-started subset; reason + blocked required):

| Section | Item | Reason | Blocked |
| ------- | ---- | ------ | ------- |
| §N … | Short item text | Why not started | What unblocks it |

Rules:

- Group by `TODO.md` section when sections exist; one row per checkbox or tight group.
- Carry forward prior skips **only** in Skipped, never also under Pending.
- Split partial checkboxes in `TODO.md`: verified slice → Done; remainder → Pending or Skipped.
- Report summarizes `TODO.md`; it does not replace updating it.

## 15. When to stop and ask (concrete triggers)

Ask rather than proceed when:

- A product requirement in `README.md` is underspecified for the task at hand, or the task depends
  on one of the pending decisions in §13.
- You'd need to introduce a new paid service, SDK, or vendor not in §4.
- A change is destructive or hard to reverse (schema drop/rename affecting existing data, deleting
  a store, force-pushing, altering a committed migration).
- Two reasonable implementations exist and the choice materially affects future work (e.g. polling
  vs websockets for order updates; which payment provider; where image storage lives).
- You are about to **`git commit`**, **`git push`**, **`gh pr create`**, **`gh pr merge`**, or
  otherwise record/publish history — always let the user review first and ask (§2.12), even if they
  approved commits or pushes in a prior session.
- A new UI state has no design-system precedent and you would otherwise invent inconsistent chrome.
- Something in this file conflicts with an explicit user instruction in the moment — surface the
  conflict, don't silently pick one.
- The task would implement an item from the product **Excluded Features** list (`README.md` §9).

Otherwise: use this file, the skills, the coding-standards rules, and good judgment, and proceed.
